# 第二章：2D游戏开发技术基础

## Core Idea
本章建立跨引擎的 2D 游戏开发“通用地基”：游戏循环与帧率无关的时间控制、对象化组织、碰撞检测、事件驱动、屏幕坐标与图形表现、向量/插值数学以及色彩表达。学完这些原理后，在 Godot 中实现只是把通用机制映射到节点与函数上。

## Frameworks Introduced
- **游戏循环（Game Loop）**：游戏是持续运行的世界，每帧循环执行“处理输入 → 更新状态 → 渲染画面”，一次循环即一帧。
  - When to use: 理解任何“为什么敌人不动时世界也在运行”、确定逻辑应写在哪个回调中。
  - How: Godot 自动管理主循环，开发者实现 `_process(delta)` / `_physics_process(delta)`，而不是自己写 while 循环。
- **帧率无关移动（Delta Time）**：两帧之间的真实时间差 Δt，是保证不同性能设备上行为一致的关键。
  - When to use: 任何基于时间的位移、计时、补间，都不允许按帧数叠加固定增量。
  - How: `position += speed * delta`；例如每秒 100 像素写成 `position.x += 100 * delta`，而不是 `+= 5`。
- **面向对象组织（OOP）**：把游戏元素视为封装属性和行为的对象；类 = 蓝图/物种，实例 = 个体。
  - When to use: 组织角色、敌人、道具、UI 等任何可复用逻辑。
  - How: 对象封装自己的数据（属性）与行为（方法），通过明确接口协作，实现模块化、高内聚低耦合、可重用、可扩展、易调试。
- **碰撞检测三类型**：AABB 矩形（角色/墙/平台）、圆形（弹丸/光环）、多边形（不规则轮廓）。
- **事件驱动机制**：程序不主动轮询，而是监听事件并在发生时执行回调；输入、碰撞、计时器都走事件。
- **精灵 / 动画分工**：精灵负责“演”（视觉），逻辑节点与脚本负责“动”（行为），视觉层与逻辑层分离。
- **色彩选择规则**：加载/渲染资源用 RGB；控制透明与过渡用 RGBA；动态变色与感官调节用 HSV。

## Key Concepts
- **Frame / FPS**：一次更新+渲染为一帧；常见 30/60/120 FPS。
- **Delta Time**：当前帧与上一帧的间隔秒数，是“帧率无关”的唯一保证。
- **AABB / 圆形 / 多边形碰撞**：由简到繁的碰撞边界描述方式。
- **CollisionShape2D**：定义碰撞形状，本身无物理属性；Area2D 感知不阻挡；CharacterBody2D 精细控制移动（自带 move_and_slide）；RigidBody2D 完全物理仿真。
- **碰撞层与遮罩（Layer/Mask）**：过滤无效碰撞计算，是性能优化基础。
- **屏幕坐标系**：Godot 2D 原点在左上角，X 向右、Y 向下为正，与数学坐标系相反。
- **Sprite2D / AnimatedSprite2D / TextureRect / TileMap**：静态精灵、帧动画、UI 图像、瓦片地图的对应节点。
- **瓦片图集（Tile Set）+ 二维数组数据**：瓦片地图的两大要素，支持为每格标记碰撞/导航/动画属性。
- **向量（Vector2）**：有方向和大小的量，用于位置、速度、力；标准化可得单位方向。
- **Lerp 插值**：从 A 朝 B 走比例 t（0–1），实现平滑过渡；Godot 提供 `lerp()`、`move_toward()` 和 Tween。
- **RGBA / HSV**：RGB 加 Alpha 通道表示透明；HSV 更贴近人对色相/饱和/明暗的感知。
- **配色模式**：互补色、类比色、分裂互补、三角色、单色。

## Mental Models
- Think of 游戏循环 as 游戏的“心跳”：每次跳动完成输入→更新→渲染，世界才持续运转。
- Think of 类与对象 as 物种与个体：猫科定义了共性，每只猫拥有不同的属性取值。
- Think of Godot 节点搭建 as 乐高积木：不同功能节点 = 不同“型号”的积木，实例可独立涂色、独立状态。
- Think of 碰撞检测 as 游戏的“触觉”：环境边界、物体交互、事件触发都靠它。
- Think of 色彩 as “无需文字就能读懂的界面”：它同时承担氛围、状态提示、行为引导、阵营区分与世界观层次。
- Think of 向量 as 一根“方向+长度”的箭头：加法合并方向，减法求指向，标量乘改变速度不改变方向。

## Anti-patterns
- **逐帧加固定位移**：`position.x += 5` 在 60 FPS 每秒 300px、30 FPS 每秒 150px，导致不同设备体验不公平；必须乘 delta。
- **所有对象两两碰撞检测**：性能指数级恶化；用 Layer/Mask 只让相关层参与计算。
- **把精灵当逻辑**：角色碰撞、移动应交给物理/脚本节点，精灵只负责显示。
- **颜色乱用、数量贪多**：游戏配色通常“主色 + 强调色 + 辅助色”就够；UI 色必须与场景色区分。
- **忽略 Y 轴方向**：把屏幕坐标当成数学坐标系导致角色上下颠倒。

## Code Examples
帧率无关移动（Godot）：
```gdscript
func _process(delta):
    # 速度单位：像素/秒，与帧率无关
    position += Vector2(100, 0) * delta
```
- **What it demonstrates**: 无论 30 还是 60 FPS，每秒位移都恒为 100 像素。

半透明精灵与 HSV 动态变色：
```gdscript
$Sprite.modulate = Color(1, 1, 1, 0.5)          # RGBA 半透明
var rainbow = Color.from_hsv(hue, 1.0, 1.0)     # 用色相生成颜色
```
- **What it demonstrates**: 不用替换贴图即可改变可见性与色调。

## Reference Tables
| 帧率 | Δt | 每帧移动（速度100） | 每秒移动 |
|---|---|---|---|
| 60 FPS | ≈0.0167s | ≈1.67 px | ≈100 px |
| 30 FPS | ≈0.0333s | ≈3.33 px | ≈100 px |

| 碰撞节点 | 职责 | 适用 |
|---|---|---|
| CollisionShape2D | 定义形状 | 所有物理碰撞的基础 |
| Area2D | 区域感应，不阻挡 | 豆子、能量豆、触发区 |
| CharacterBody2D | 脚本精细控制+自动滑动 | 玩家、可控制角色 |
| RigidBody2D | 物理引擎全仿真 | 木箱、落石 |

| 色彩模型 | 首选场景 | Godot 示例 |
|---|---|---|
| RGB | 静态资源加载/精确定色 | `Color(1, 0, 0)` |
| RGBA | 透明、淡入淡出、特效 | `modulate = Color(1,1,1,0.5)` |
| HSV | 动态变色、渐变 | `Color.from_hsv(h, s, v)` |

## Worked Example
作者用《吃豆人》贯穿本章：每帧循环里，输入阶段读取方向键；更新阶段计算吃豆人新坐标、驱动四只幽灵的追踪 AI、做碰撞检测（碰到豆子加分、碰到能量豆让幽灵进入“害怕”状态、碰到幽灵判定胜负）；渲染阶段绘制嘴巴张合的吃豆人、变蓝闪烁的幽灵与跳动分数。开发者只需把自己的对象写进“更新状态”这一步，其余交给引擎循环。

## Key Takeaways
1. 一切基于时间的逻辑都要乘 delta，帧率无关是实时游戏的第一原则。
2. 用对象组织游戏元素，职责单一、接口协作，避免一坨全局逻辑。
3. 先选正确的碰撞类型，再配合 Layer/Mask 控制开销。
4. Godot 中视觉节点只负责“演”，移动碰撞等逻辑由物理节点和脚本负责。
5. 向量标准化后再乘速度，避免斜向移动比直向快（1.414 倍）。
6. 选颜色先问“要传达什么”，RGB/RGBA/HSV 按任务各司其职。
